Static Connectivity Tab

Located at static_analyzer/tabs/static_connectivity_tab.py, the Connectivity Tab (implemented as the mixin class StaticFluidFlowTab) addresses a fundamentally different and complementary question to FracSTAT's geometry-focused tabs: how are fractures connected to one another, and what does that connectivity imply about the ability of the network to transmit fluid, accommodate strain, or compartmentalise a reservoir?

This module implements the topological node-counting and branch-classification methodology pioneered by Sanderson and co-workers (Sanderson & Nixon, 2015; Manzocchi, 2002) and widely used in reservoir characterisation, tunnelling, groundwater hydrology, and CO₂ storage studies. It operates exclusively on data carrying real map geometry — SVG-digitised trace maps or spatial Excel/CSV imports — and is the only Static Analyzer tab that performs its own expensive O(n²) geometric pre-processing step to detect pairwise segment intersections.

The module performs four closely related tasks: classifies every fracture-trace tip and every trace-to-trace intersection into one of three topological node types (I, Y, X); walks each trace and cuts it at its nodes to obtain true topological branches, classifying each branch by the connectedness of its two ends; computes a battery of scalar connectivity statistics; and renders six selectable diagrams — a spatial node map, four individual ternary diagrams, and a combined 2×2 ternary dashboard — that let the analyst see at a glance where the network sits on the spectrum between a poorly connected "scattered" network and a well-connected "lattice" network.

2. Data Input

2.1 Upstream Data Source

The Connectivity tab does not load files directly. It consumes the same per-segment results DataFrame (self.results) produced by the Static Analyzer's shared geometry engine after an SVG or spatial Excel/CSV file is loaded, and reacts passively whenever results change via the refresh_static_fluidflow() hook called from StaticAnalyzerApp.refresh_all_tabs().

2.2 Required Columns

ColumnDescription
TraceInteger or string identifier grouping segments belonging to the same digitised fracture trace.
SegmentInteger identifier of a segment within its trace, used to order segments when extracting trace endpoints.
X1, Y1, X2, Y2Real-world (scaled) coordinates of each segment's two endpoints, in the project's selected display unit (m, cm, mm, or km).

2.3 Data-Source Gating

Before any computation is attempted, the tab checks whether the loaded data actually carries genuine spatial geometry. SVG-digitised trace maps and spatial Excel/CSV imports are accepted. Legacy orientation-only formats (ID/Strike/Dip tables, Trend/Plunge pole tables) are explicitly rejected with an explanatory message — node counting on synthetic orientation-wheel coordinates would be meaningless without real spatial position. The rejection test inspects whether the first loaded Segment object carries a non-null _preset_strike attribute, set only by the Excel loader for orientation-only formats.

Note: when an orientation-only format is detected, all six canvases display "I-Y-X connectivity needs map geometry; load an SVG or spatial CSV/Excel" rather than raising an error.

2.4 Unit Handling

The tolerance entry field and all reported lengths and areas automatically track the project's currently selected display unit (obtained from _static_map_unit_var, defaulting to metres). The node-snap-tolerance label refreshes on every draw to show the active unit in parentheses — e.g. "Node snap tolerance (m)" or "Node snap tolerance (cm)".

4. Mathematical Background

Let S = {s₁, …, s_n} be the set of digitised segments, each defined by two endpoints (x1, y1) and (x2, y2) belonging to a parent trace.

4.1 Node Classes

Following the terminology introduced for fracture network topology (Manzocchi, 2002; Sanderson & Nixon, 2015), every distinct point where the network terminates or crosses itself is classified into exactly one of three mutually exclusive categories. The classification is a property of the trace, not of the individual straight segments a polyline happens to be digitised with: only the first point of a trace's first segment and the last point of its last segment are trace tips, and interior polyline vertices are never nodes.

SymbolNameGeometric DefinitionBranchesGeological Meaning
IIsolated nodeA trace tip that does not lie within snap tolerance of the interior of any other trace.1A fracture tip that terminates in intact rock — propagation stopped without linking to another fracture.
YAbutting nodeA tip of one trace lying on the interior of another trace.3One fracture terminated against an earlier through-going fracture — the classic "T" intersection recording a relative age relationship.
XCrossing nodeTwo trace interiors crossing, with the intersection point at a tip of neither trace.4Two fractures crossed each other, implying both were open/active at the time of intersection or that a younger fracture propagated straight through an older one.
Tip-to-tip contacts. Two trace tips that merely touch each other form a 2-branch contact, which is none of I, Y or X. Both tips are retained as I nodes and no Y node is recorded. Calling such a contact a Y node would assert that three branches meet where only two do, which breaks the node-degree identity N_B = (N_I + 3·N_Y + 4·N_X) / 2 and produces a non-integer branch count.

4.2 Node-Level Statistics

N = N_I + N_Y + N_X (total node count) CF = (N_Y + N_X) / N (connected fraction) N_B = (N_I + 3·N_Y + 4·N_X) / 2 (branches implied by the node census) C̄ = (3·N_Y + 4·N_X) / N_B (average connections per branch)

The connected fraction CF expresses what proportion of all identified nodes actually represent a connection between two or more fractures, as opposed to a dead end. It ranges from 0 (a network of entirely isolated fractures) to 1 (every node is a connection). The average connections per branch C̄ counts the total number of branch ends that terminate at Y- or X-nodes (3 per Y-node, 4 per X-node) and divides by the total number of branches N_B. Isolated I-nodes contribute only to the denominator, depressing C̄; a fully connected lattice with no I-nodes would approach the theoretical maximum C̄ = 2.

The identity N_B = (N_I + 3·N_Y + 4·N_X) / 2 is the node-degree relation of Sanderson & Nixon (2015, eq. 5): summing the branch ends meeting at every node counts each branch exactly twice. Because every node contributes an integer number of ends, the sum is always even and N_B is always an integer for a correctly classified network — a non-integer result is a diagnostic that some contact has been given the wrong node class.

Two branch counts, deliberately. The module reports two quantities that should agree. result.branch_count is obtained by walking each trace and cutting it at its nodes (Section 4.4); result.branch_count_from_nodes applies the identity above to the node census. Their agreement is a genuine internal check on the node classification. They diverge, legitimately, when boundary tips have been censored: the node formula has no way to account for I nodes that were removed, so it under-counts relative to the walked branch population. Note that connections_per_branch (C̄) divides by the node-derived N_B, so C̄ and C_B in Section 4.5 are the same number by construction, not two independent estimates.

4.3 Dimensionless Intensity (B₂₂ and P₂₂)

B₂₂ = L_total² / (A · N_B) (branch-normalised intensity — result.dimensionless_branch_intensity) P₂₂ = L_total² / (A · N_traces) (trace-normalised intensity — result.dimensionless_trace_intensity)

B₂₂ is the square of the cumulative trace length L_total, divided by the sample area A and further normalised by the total branch count N_B, following Sanderson & Nixon (2015, eq. 9). It is a scale-independent measure of overall fracture density that can be compared directly between outcrops of different sizes. ConnectivityResult also exposes a companion, trace-normalised measure, P₂₂, computed the same way but dividing by the number of distinct traces (trace_count) instead of the branch count. P₂₂ is available on the result object for programmatic use but is not currently surfaced as a sidebar statistic in the Connectivity tab.

N_B here is the topological branch count — trace portions between nodes — so B₂₂ does not change when a trace is re-digitised with more vertices. Substituting the raw segment count would make B₂₂ scale inversely with digitisation density and destroy comparability between hand-digitised and curve-sampled SVG traces.

The area A is the area of the sampling window. When a window is entered in the sidebar (Section 3.1) that window's area is used; otherwise A falls back to the bounding box of the digitised traces, which makes B₂₂ and P₂₂ conditional on the traces themselves rather than on an independently chosen sample domain.

4.4 Branch Classification

A branch is the portion of a trace between two nodes. It is not the same thing as a digitised segment: an isolated trace drawn with one straight segment and the same trace drawn with fifty both contain exactly one branch. The module therefore walks each trace in digitised order and cuts it only where a node falls — at an X or Y node inside a segment, or at an interior polyline vertex that happens to coincide with a node. Interior vertices that are not nodes never cut. Each resulting branch has its two ends tested for proximity to the accepted X∪Y node set and labelled C (connected) or I (isolated):

ClassEnd PatternSymbolMeaning
I–Iisolated – isolatedn_iiA fully isolated strand that neither terminates against nor is crossed by any other fracture at either end.
I–Cisolated – connectedn_icA branch that dangles freely at one end but connects to the network at the other — a "dead-end spur".
C–Cconnected – connectedn_ccA branch connected to the rest of the network at both ends — the fully connected, fluid-conducting portion of the fracture set.
N_B = N_II + N_IC + N_CC

This walked census is the value reported as result.branch_count and used in B₂₂. It is cross-checked against the node-derived count of Section 4.2.

4.5 Line- and Branch-Density Ratios (C_L and C_B)

N_L = (N_I + N_Y) / 2 C_L = 2·(N_X + N_Y) / N_L N_Br = (N_I + 3·N_Y + 4·N_X) / 2 C_B = (3·N_Y + 4·N_X) / N_Br

N_L is an estimate of the number of discrete "lines" (through-going fracture traces) implied by the node population, and C_L (connections per line) expresses how many connections, on average, each such line participates in. N_Br applies the node-degree identity of Section 4.2, so C_B is numerically identical to the connections_per_branch property; the independent cross-check on the branch population is branch_count from the trace walk, not C_B.

4.6 Ternary (Barycentric) Coordinates

Each of the four ternary diagrams plots a data point inside an equilateral triangle using standard barycentric-to-Cartesian conversion. For any three proportions p_bl, p_br, p_apex that sum to 1, the Cartesian plotting position within a unit-height triangle is:

bx = p_br + 0.5 · p_apex by = (√3 / 2) · p_apex

For the I-Y-X ternary, the vertex assignment is bottom-left = Y fraction, bottom-right = X fraction, apex = I fraction (i.e. p_i = N_I/N, p_y = N_Y/N, p_x = N_X/N). For the Branch Topology ternary, the three proportions are the I-I, I-C, and C-C branch fractions: p_ii at the apex, p_cc at bottom-right, p_ic at bottom-left.

4.7 Theoretical Random-Network Locus (Branch Topology Ternary)

The Branch Topology diagram overlays a reference curve corresponding to the theoretical relationship expected for a network where node connectivity follows a simple binomial (random) model. Parameterising by C_B ∈ [0, 2] and setting p_C = C_B / 2:

p_II = (1 − p_C)² p_CC = p_C² p_IC = 2·p_C·(1 − p_C)

The locus is plotted as a smooth blue curve with tick marks at C_B = 0.0, 0.5, 1.0, 1.5, 2.0, giving the analyst an immediate visual reference for how far the observed network departs from a purely random connectivity structure. Real fracture networks are typically displaced toward the C-C corner relative to this random-model curve.

5. Algorithms

The complete node-classification and branch-typing pipeline is implemented in core/branch_counter.py, function count_iyx_nodes(), and is called from the GUI layer only when a recompute is actually required (Section 10).

5.1 Pre-processing and Validation

If the results table is empty or missing any of the required geometry columns (Trace, Segment, X1, Y1, X2, Y2), the function immediately returns an all-zero ConnectivityResult. All coordinate columns are coerced to numeric (pandas.to_numeric, errors='coerce'); rows that fail conversion are dropped. Segments shorter than 1×10⁻¹² are discarded as degenerate. The tolerance is clamped to be non-negative (max(tolerance, 0.0)). Two rectangles are then established: the bounding box of the surviving coordinates (data_bounds), and the reported sampling window (bounds), which is the caller-supplied sample_bounds when one is given and otherwise falls back to data_bounds. The reported window anchors both the boundary-exclusion test and the sample area A used by B₂₂ and P₂₂.

A per-trace tip lookup is also built by _trace_tip_lookup(), mapping each trace to the two coordinates that are genuinely its tips. This is what makes the node classification in Section 5.3 a trace-level rather than a segment-level test.

5.2 Pairwise Segment Intersection

For every distinct pair of segments belonging to different traces (segments sharing the same Trace identifier are never tested against each other), the module solves the standard 2-D parametric line intersection system:

P = A₁ + u₁·(A₂ − A₁) = B₁ + u₂·(B₂ − B₁) denominator = dy₂·dx₁ − dx₂·dy₁ If |denominator| < 1×10⁻¹² → segments are parallel; no intersection recorded. Otherwise solve for u₁ (ua) and u₂ (ub) algebraically. L₁ = length(A), L₂ = length(B) tol_a = tol / L₁, tol_b = tol / L₂ Intersection accepted if both: −(tol_a + ε) ≤ ua ≤ 1 + (tol_a + ε) −(tol_b + ε) ≤ ub ≤ 1 + (tol_b + ε) where ε = 1×10⁻¹⁰.

The tolerance is converted from an absolute map distance into a fractional parametric extension (tol_a = tol / L₁, tol_b = tol / L₂) so that the snap distance scales correctly with segment length. The accepted point is then computed by substitution back into the first segment's parametric equation, with ua and ub clamped to [0, 1].

5.3 Classifying the Intersection: Abutment vs Crossing

Each accepted intersection is tested against the tips of the parent traces, not against the endpoints of the two segments that happened to intersect. _at_trace_tip() compares the intersection point, by Euclidean distance under the user-specified tolerance, against the two tips of trace i and then against the two tips of trace j. This yields two booleans — tip_i and tip_j — and the classification follows a four-way decision table:

tip_itip_jNode classSplits recorded
TrueTruenone — 2-branch tip-to-tip contact; both tips stay I nodesnone
TrueFalseY (trace i abuts trace j)segment j at ub
FalseTrueY (trace j abuts trace i)segment i at ua
FalseFalseX (two trace interiors cross)both segments at their respective u-values

Testing segment endpoints instead would call an interior polyline vertex a trace tip and so downgrade a genuine 4-branch crossing to a 3-branch Y node — an error that grows with digitisation density, because the denser a polyline is sampled the more interior vertices there are to be mistaken for tips. Splits are recorded whenever the relevant clamped parametric coordinate lies strictly inside (0, 1); those coordinates populate the per-segment seg_splits table used for the branch walk.

5.4 Trace-Tip (I-node) Extraction and Boundary Exclusion

Independently of the pairwise intersection search, the true tips of every trace are extracted by _trace_endpoints(): segments are grouped by Trace and sorted by Segment, and the first coordinate of the first segment and the second coordinate of the last segment in each trace are taken as the two trace-tip candidates — correctly handling multi-segment traces even though the trace is stored as a chain of individual straight segments.

I nodes are counted per trace tip, not per unique location. Because _trace_endpoints() already emits exactly two points per trace there are no floating-point duplicates to merge, and no clustering is applied to them. Clustering here would collapse the two distinct tips of a tip-to-tip contact into a single node, and the branch-end bookkeeping would break: N_B = (N_I + 3·N_Y + 4·N_X) / 2 would stop being an integer. Each tip contributes exactly one branch end.

If "Include boundary I-nodes" is off (the default) and a sampling window has been supplied, every candidate tip lying within tolerance of a side of that window is discarded by _on_boundary(). This censoring correction reflects the fact that a trace exiting the mapped area is not truly an isolated fracture tip — it is an artefact of the finite sample window.

Why the window is required. Boundary I nodes can only be identified relative to a window chosen independently of the traces, as Mauldon, Dunne & Rohrbaugh (2001) require. If the window were derived from the traces themselves, the extremal tips would define the box and therefore always lie on it, so the exclusion would delete them regardless of whether they are genuine fracture terminations — removing I nodes and biasing C_L and C_B upward. For that reason exclude_boundary_i is honoured only when sample_bounds is supplied; with no window the switch has no effect and every tip is retained.

5.5 Point Clustering

Because floating-point intersection arithmetic can produce several near-duplicate points representing the same physical intersection, the raw X and Y candidate sets are merged by _cluster_points() using a greedy single-pass algorithm: each new candidate point is compared, in the order encountered, against the running centroid of every cluster created so far. If it lies within tolerance of an existing cluster centroid, it is merged and the centroid is updated as the incremental running mean; otherwise a new cluster is started. As noted in Section 5.4, I-node candidates are deliberately excluded from this step.

5.6 Priority-Ordered De-duplication Across Classes

After clustering, three independent point sets exist. Any Y candidate also matching an X cluster is removed via _remove_points_near() (a true crossing takes priority over a coincidental abutment). Any I candidate matching an X or Y cluster is removed (a genuine intersection always takes priority over an apparent near-miss tip). This produces the strict, mutually exclusive priority ordering X > Y > I, ensuring every physical location is counted exactly once in its most topologically significant category.

5.7 The Branch Walk and Classification

The final stage (_classify_branches) counts branches by walking each trace, not by subdividing each segment. Segment rows are grouped by Trace and ordered by Segment so the walk follows the trace as digitised. For each trace an ordered list of cut points is assembled from two sources: every X/Y node recorded in seg_splits that falls inside one of its segments, and any interior polyline vertex that itself coincides with a node. Interior vertices that are not nodes never cut, which is what makes the branch count independent of digitisation density.

The trace's own start and end are then prepended and appended, consecutive points closer than the tolerance are collapsed, and each consecutive pair defines one branch. Both of its ends are tested against the merged X∪Y node set by is_connected() and the branch is assigned to the I-I, I-C or C-C class. A trace with no cuts contributes exactly one branch.

python 
def count_iyx_nodes(results, tolerance=1.0, exclude_boundary_i=True,
                    progress_callback=None, sample_bounds=None):
    """Classify I/Y/X nodes and I-I/I-C/C-C branches from spatial trace data.

    Nodes are classified by TRACE-level topology (Sanderson & Nixon 2015):
    I = isolated trace tip (1 branch), Y = a tip abutting another trace's
    interior (3 branches), X = two trace interiors crossing (4 branches).
    Two tips that merely touch form a 2-branch contact, which is none of
    I/Y/X; both tips stay I nodes.

    ``sample_bounds`` is the independently defined sampling window
    (xmin, ymin, xmax, ymax).  ``exclude_boundary_i`` is honoured only when
    it is supplied, because boundary tips cannot be identified against a
    window derived from the traces themselves.
    """
    if results is None or results.empty:
        return _empty_result()

    cols = ("Trace", "Segment", "X1", "Y1", "X2", "Y2")
    missing = [c for c in cols if c not in results.columns]
    if missing:
        raise ValueError(f"Missing geometry column(s): {', '.join(missing)}")

    segs = results[list(cols)].copy()
    for col in ("X1", "Y1", "X2", "Y2"):
        segs[col] = pd.to_numeric(segs[col], errors="coerce")
    segs = segs.dropna(subset=["X1", "Y1", "X2", "Y2"])

    xy = segs[["X1", "Y1", "X2", "Y2"]].to_numpy(dtype=float)
    traces = segs["Trace"].to_numpy()
    lengths = np.hypot(xy[:, 2] - xy[:, 0], xy[:, 3] - xy[:, 1])
    valid = lengths > 1e-12
    xy, traces, segs, lengths = xy[valid], traces[valid], segs.iloc[np.nonzero(valid)[0]], lengths[valid]

    tol = max(float(tolerance), 0.0)
    xs, ys = np.concatenate([xy[:, 0], xy[:, 2]]), np.concatenate([xy[:, 1], xy[:, 3]])
    data_bounds = (float(xs.min()), float(ys.min()), float(xs.max()), float(ys.max()))

    # The reported window is the caller's sampling window when one is known;
    # otherwise it falls back to the data extent, which makes every intensity
    # measure conditional on the traces themselves.
    bounds = tuple(float(v) for v in sample_bounds) if sample_bounds is not None else data_bounds
    sample_area = max((bounds[2] - bounds[0]) * (bounds[3] - bounds[1]), 0.0)

    segment_order = segs["Segment"].to_numpy()
    trace_tips = _trace_tip_lookup(segs)          # trace id -> its two TIPS

    x_candidates, y_candidates = [], []
    seg_splits = defaultdict(list)

    # Pairwise intersection search (O(n^2), cross-trace pairs only)
    for i in range(len(xy)):
        for j in range(i + 1, len(xy)):
            if traces[i] == traces[j]:
                continue
            hit = _segment_intersection(xy[i], xy[j], tol)
            if hit is None:
                continue
            x, y, ua, ub = hit

            # Topology is a property of the TRACE, not of the arbitrary segment
            # a polyline happens to be broken into.
            tip_i = _at_trace_tip(x, y, trace_tips.get(traces[i]), tol)
            tip_j = _at_trace_tip(x, y, trace_tips.get(traces[j]), tol)

            if tip_i and tip_j:
                continue                      # 2-branch contact: both stay I
            if tip_i and not tip_j:
                y_candidates.append((x, y))
                if 0.0 < ub < 1.0:
                    seg_splits[j].append((ub, x, y))
            elif tip_j and not tip_i:
                y_candidates.append((x, y))
                if 0.0 < ua < 1.0:
                    seg_splits[i].append((ua, x, y))
            else:
                x_candidates.append((x, y))   # two trace interiors cross
                if 0.0 < ua < 1.0:
                    seg_splits[i].append((ua, x, y))
                if 0.0 < ub < 1.0:
                    seg_splits[j].append((ub, x, y))

    # Cluster X and Y only, then de-duplicate with priority X > Y > I
    x_nodes = _cluster_points(x_candidates, tol)
    y_nodes = _remove_points_near(_cluster_points(y_candidates, tol), x_nodes, tol)

    endpoint_candidates = _trace_endpoints(segs)
    if exclude_boundary_i and sample_bounds is not None:
        endpoint_candidates = [p for p in endpoint_candidates
                               if not _on_boundary(p, bounds, tol)]

    # I nodes are counted per TRACE TIP, not per unique location: clustering
    # here would merge the two tips of a tip-to-tip contact into one node and
    # N_B = (N_I + 3*N_Y + 4*N_X)/2 would stop being an integer.
    i_nodes = (np.asarray(endpoint_candidates, dtype=float)
               if endpoint_candidates else np.empty((0, 2), dtype=float))
    i_nodes = _remove_points_near(i_nodes, x_nodes, tol)
    i_nodes = _remove_points_near(i_nodes, y_nodes, tol)

    # Branches counted by walking each trace and cutting only at its nodes
    n_ii, n_ic, n_cc = _classify_branches(
        xy, traces, segment_order, x_nodes, y_nodes, tol, seg_splits
    )
    branch_count = n_ii + n_ic + n_cc

    return ConnectivityResult(
        i_nodes=i_nodes, y_nodes=y_nodes, x_nodes=x_nodes,
        bounds=bounds, trace_count=int(pd.Series(traces).nunique()),
        segment_count=int(len(xy)), branch_count=branch_count,
        total_length=float(lengths.sum()), sample_area=float(sample_area),
        n_ii=n_ii, n_ic=n_ic, n_cc=n_cc,
    )

5.8 Algorithm Complexity Summary

StageComplexityNotes
Pairwise intersection search (first pass)O(n²)n = number of segments; every cross-trace pair is tested once.
Point clusteringO(k²) per classk = raw candidate count for X or Y, typically ≪ n². I-node candidates are not clustered.
Trace-tip lookupO(n log n)One sort of the segment table by (Trace, Segment); two tip coordinates stored per trace.
Boundary exclusionO(m)m = number of trace-tip candidates (2 per trace). Skipped entirely when no sampling window is supplied.
Branch walk & classifyO(n · s)s = cuts per segment; uses seg_splits accumulated during the first pass, so no repeated O(n²) intersection search.

The dominant cost is quadratic in the number of segments. For very dense SVG traces (many thousands of short curve-sampled segments), this can become the single most expensive computation in the entire Static Analyzer workspace.

6. Statistical Methods

Unlike the Histogram or CDF tabs, the Connectivity module does not perform inferential statistics. Its statistical content is entirely descriptive and topological: it counts, classifies, and ratios discrete network elements. All reported quantities are deterministic functions of the digitised geometry and the three user-controlled parameters (snap tolerance, sampling window, boundary-I-node inclusion). No sampling error or estimator variance is associated with these numbers in the classical statistical sense.

8. Step-by-Step Example Workflows

8.1 Assessing Reservoir Connectivity from an Outcrop Trace Map

  1. Load an SVG trace map (or a spatial Excel/CSV) into the Static Analyzer and confirm the Fracture Map tab renders correctly with calibrated scale.
  2. Open the Connectivity tab. Because the data is new, the tab is marked stale and an automatic lazy computation runs immediately with the default 0.1-unit tolerance.
  3. Inspect the I-Y-X Connectivity Nodes map. Visually confirm that crossing (blue) markers sit at genuine X-shaped intersections, and abutting (green) markers at T-shaped terminations. If many genuinely touching fracture tips are coloured red (I), the snap tolerance is too small relative to digitisation precision; if unrelated nearby fractures are merged into a single node, the tolerance is too large.
  4. Adjust "Node snap tolerance" as needed (e.g. from 0.1 m to 0.25 m for coarse digitisation) and press "↻ Recalculate".
  5. Decide on boundary I-nodes: use exclusion (the default) for an arbitrary rectangular crop of a larger fracture field; use inclusion if fracture tips genuinely terminate at a natural geological boundary such as a bounding fault.
  6. Read the I-Y-X Summary card: for example, I = 42, Y = 118, X = 76, Total = 236, Branches = 310, CF = 0.822, C̄ = 0.877, B₂₂ = 4.6.
  7. Switch to the I-Y-X Ternary diagram — a point sitting close to the Y-X edge (away from the I apex) indicates a well-connected network.
  8. Switch to the C_L diagram — a point to the right of the dashed C_L = 3.57 contour indicates a topologically well-connected, likely-percolating regime.
  9. Switch to the Branch Topology diagram — a point displaced toward the C-C corner relative to the random-network locus suggests connectivity in excess of a purely random linking process, consistent with mechanically controlled fracture growth.
  10. Use "⬇ Save Image" on each diagram of interest to export 300 dpi PNGs to the project's FracSTAT_plot_exports folder for inclusion in a report or publication.

8.2 Worked Numerical Example

Consider a network reporting I = 10, Y = 20, X = 10 (N = 40 nodes). The node census fixes the branch population before any branch is walked: the branch ends sum to 10·1 + 20·3 + 10·4 = 110, so N_B = 110 / 2 = 55. Ten of those ends are isolated, so the walked census must satisfy 2·N_II + N_IC = 10 and N_II + N_IC + N_CC = 55 — for instance N_II = 0, N_IC = 10, N_CC = 45. The connectivity statistics are:

CF = (20 + 10) / 40 = 0.75 N_B = (10 + 3·20 + 4·10) / 2 = 110/2 = 55 (must equal N_II + N_IC + N_CC = 0 + 10 + 45) C̄ = (3·20 + 4·10) / 55 = 100/55 ≈ 1.82 N_L = (10 + 20) / 2 = 15 C_L = 2·(10 + 20) / 15 = 4.0 C_B = (3·20 + 4·10) / 55 = 100/55 ≈ 1.82 (identical to C̄ by construction)

The agreement between 55 and 0 + 10 + 45 is the check worth performing on real data. A mismatch means either that boundary tips were censored — in which case the node formula legitimately under-counts, because the removed I nodes are missing from it — or that a contact has been given the wrong node class. A non-integer N_B is always the second case.

With C_B = 1.82 exceeding the well-connected reference value of 1.7–1.8 commonly cited in topological classifications, and C_L = 4.0 exceeding the 3.57 percolation-related threshold, this hypothetical network would be characterised as well connected and likely to behave as an effective fluid-flow pathway network.

9. Geological Interpretation

9.1 Connectivity Statistics and Fluid Flow

Fracture connectivity, not fracture density alone, is frequently the controlling factor in whether a naturally fractured reservoir, aquifer, or rock mass behaves as an effective flow or mechanical system. Two intervals with identical fracture intensity (P10, P21, or B₂₂) can have dramatically different bulk permeability if one is dominated by isolated fractures (high I-node fraction, low CF) while the other forms an interconnected lattice (high X/Y-node fraction, high CF).

9.2 Node-Type Ratios and Network Maturity

Increasing abundance of crossing (X) nodes relative to abutting (Y) nodes is often associated with a more mature, multiply-reactivated fracture system where successive fracture sets have propagated through pre-existing fractures rather than systematically terminating against them. Conversely, a network dominated by Y-nodes frequently records a clear relative-age sequence, with younger, shorter fractures terminating against an earlier, more continuous fracture set — a pattern common in systematically jointed sedimentary sequences with a dominant bedding-perpendicular joint set.

9.3 Percolation and Effective Connectivity Thresholds

The C_L = 3.57 and C_B ≈ 2 reference values on the ternary diagrams derive from topological/percolation-theory studies of two-dimensional fracture networks (see Section 13, References), where networks below the threshold are statistically unlikely to form a fully connected percolating cluster spanning the sample domain, while networks above typically do. These are heuristic reference values rather than universal physical constants: the true percolation threshold for any specific network depends on the fracture-length distribution, orientation distribution, and aperture/permeability contrast, quantified separately in other FracSTAT tabs.

9.4 Dead-End Branches (I-C) and Hydraulic Significance

A large I-C (dead-end spur) fraction indicates that a substantial portion of the mapped fracture length — while nominally connected to the main network at one end — terminates in intact rock at the other and cannot itself provide a through-going flow path. Distinguishing the C-C (fully connected, potentially conductive) branch population from the I-C and I-I populations is therefore directly relevant when the Connectivity results are combined with permeability up-scaling or discrete-fracture-network flow simulation performed outside FracSTAT.

9.5 Scale Dependence and Sampling Considerations

Connectivity statistics are not fully scale-invariant: the observed I-node fraction is sensitive to the size of the mapped domain relative to the mean fracture length, because a larger domain captures more complete fracture traces (fewer artificial edge terminations). The boundary-I-node exclusion option partially corrects for this effect, but only when a sampling window has been entered — it is the window edge that defines an artificial termination. Analysts should still be cautious when comparing connectivity statistics computed from maps of substantially different physical size or aspect ratio.

10. Performance Optimization

Because the underlying topological computation is O(n²) in the number of digitised segments, the Connectivity tab is deliberately engineered to run this computation as rarely as possible while still guaranteeing that displayed statistics are always correct and current.

10.1 Result Caching

The single ConnectivityResult object produced by the most recent successful call to count_iyx_nodes() is retained in self._fluid_connectivity for the lifetime of the workspace session. Every cosmetic redraw (colour change, grid toggle, node-label toggle, pan, zoom, Reset View) reuses this cached object directly rather than recomputing it.

10.2 Lazy, On-Demand Computation

The tab is only ever computed when it is both (a) marked stale by a genuine geometry change and (b) actually the currently visible tab (or explicitly forced via Recalculate or a settings change that mandates recomputation). If the analyst never opens the Connectivity tab, the expensive computation never runs at all, regardless of how many files are loaded or how many times the profile scale is changed elsewhere in the workspace.

10.3 Geometric Fingerprinting

Every time refresh_static_fluidflow() is called, it computes a cheap fingerprint of the current results table — the tuple (row count, rounded total segment length). The fingerprint is O(1) to compare and O(n) to compute, several orders of magnitude cheaper than the O(n²) computation it guards. It changes only when the underlying digitised geometry itself has changed, remaining completely insensitive to purely cosmetic changes such as colour, font, or grid visibility.

10.4 Deferred Execution and UI Responsiveness

Because the algorithm can take perceptible wall-clock time for dense digitisations, every user action that may trigger a recompute is scheduled through Qt's after(100, …) mechanism rather than executed synchronously. This 100 ms delay is sufficient for the global loading overlay to be physically painted to the screen before the main thread blocks on the O(n²) search, so the application never appears to freeze without explanation.

10.5 Single-Figure-per-Diagram Construction

All five Matplotlib Figure/Axes/Canvas triples are constructed exactly once at tab-build time and simply shown/hidden thereafter. This avoids the overhead of destroying and rebuilding Matplotlib canvases every time the analyst switches between the five available diagrams, at the modest cost of holding five figures in memory simultaneously.

10.6a Session Restore Behaviour

Restoring a saved session sets the active tab via tabs.set(), which does not fire the same tab-click handler that normally triggers a draw when the analyst manually switches to the Connectivity tab. To prevent the diagrams from appearing blank until the analyst clicks away and back, refresh_static_fluidflow() now checks whether a cached ConnectivityResult already exists for a non-stale, non-active Connectivity tab and, if so, draws it immediately (recalculate=False) so the plots are ready the instant the tab is opened.

10.6 Recommended Practice for Large Data Sets

For SVG traces exceeding several thousand segments, consider increasing the Curve step (px) parameter when loading the SVG to reduce the number of straight-line segments used to approximate curved traces. Adjust the snap tolerance thoughtfully before pressing Recalculate rather than repeatedly nudging it — each change re-triggers the full O(n²) computation. Leave "Show node labels" off for very dense networks, as densely overlapping text labels can noticeably slow down canvas rendering and obscure the spatial map.

11. Advanced Features

11.1 Interactive Pan and Zoom

All five canvases share a common pair of mouse-driven navigation handlers connected at tab-build time. The scroll wheel (_on_scroll_zoom) zooms in or out by a fixed 1.2× factor per click, centred exactly on the cursor position so that the data-space coordinate under the cursor is held fixed while the axis limits are rescaled around it. Left-click drag (_on_mouse_press / _on_mouse_drag / _on_mouse_release) pans the active diagram by translating both axis limits by the same data-space displacement as the cursor. "↺ Reset View" restores the default extent without any recomputation.

11.2 Custom Colour Picker

Every colour swatch in the Display Settings sidebar opens the shared FracSTAT colour-picker dialog (_StaticColorButton), which presents a curated 8×5 matrix of 40 professionally chosen preset swatches spanning eight hue families at five lightness levels, plus a free-form hex-code entry field with a live preview patch. Selecting a preset or typing a valid hex code and pressing "Apply" immediately re-fires the connectivity redraw callback bound to that colour variable.

11.3 Calibrated Background Photograph Overlay

The Connectivity tab supports overlaying a real, scale-calibrated photograph of the outcrop behind the spatial node map (the four ternary diagrams do not use a background image). The implementation (_autodetect_fluid_bg_image_path()) searches in priority order: (1) an image path already stored in this tab's own StringVar; (2) the Fracture Map tab's own calibrated background image variable, if set; (3) a sidecar PNG automatically saved alongside a traced SVG by the Trace Map tool (named <svg-basename>_bg.png). The chosen path is cached in memory so repeated redraws do not re-read the file from disk. The image is drawn with imshow, its extent locked to the bounding box of the current fracture geometry, and its opacity controlled by the Image opacity entry.

12. Limitations

LimitationDescription
Greedy point-clusteringThe order-dependent greedy clustering algorithm can produce weakly order-dependent cluster centroids in rare pathological configurations of closely spaced, nearly-collinear candidate points. In practice, at sensible tolerances, this has negligible effect on reported statistics.
Heuristic reference contoursThe C_L = 3.57 and C_B ≈ 2 reference contours are values drawn from the published topological fracture-network literature and are not dynamically recalculated for the specific length or orientation distribution of the loaded data set.
Rectangular boundary assumptionThe sampling window is a rectangle. For irregularly shaped mapped areas, boundary I-node exclusion can over- or under-exclude genuine edge-truncated tips relative to the true panel outline. Leaving the window blank falls back to the trace bounding box, in which case no tip can be identified as a boundary tip at all and every tip is counted as an I node.
